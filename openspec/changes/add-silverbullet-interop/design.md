## Context

See proposal.md for motivation. Relevant current state:

- Bibliophage stores documents as Postgres rows (`documents.content` as text), with a governed tag model (names created only through `TagService`; values open, auto-create on assignment — see the `define-and-assign-tags` change) and derived state (pgvector chunk embeddings, `GraphService` nodes/edges) that must stay consistent with `content` after any edit.
- SilverBullet stores a space as markdown files, but its storage layer is already abstracted behind a small, five-method `SpacePrimitives` trait (`fetch_file_list`/`get_file_meta`/`read_file`/`write_file`/`delete_file`), exposed over a plain HTTP surface (`GET/PUT/DELETE /.fs/{path}`, `GET /.fs` for listing). The web client talks to this surface live and, by default, keeps no independent local copy — there is no local state to keep honest against, provided SilverBullet's offline/PWA sync mode is never engaged for this space (see Risks).
- SilverBullet has no server-to-client push channel of any kind (confirmed: no WebSocket/SSE in the server or client beyond the plug worker sandbox), and its rename/link-rewrite behavior (`index.renamePageCommand`) is a client-only command driven by a human action, operating over the same live `/.fs` calls. The server cannot trigger it remotely.
- SilverBullet tags (`#hashtag`, YAML `tags:` list) are flat and ungoverned — anyone can mint a new one by typing it. This is the opposite of bibliophage's tag-name governance and must never be allowed to bypass it.
- SilverBullet's hashtag grammar permits `/` and `:` inside a tag body (`#genre/fantasy` parses as one token), which maps cleanly onto bibliophage's `(tag name, tag value)` pairs — this is the encoding used both for rendering tags on read and for validating/reconciling them on write (see Decisions).
- `graph.proto`'s `Edge` message (`id`, `relationship`, `directed`, `node_a`, `node_b`) has no field recording how an edge was established.

## Goals / Non-Goals

**Goals:**
- Let documents be authored and edited via SilverBullet while bibliophage's Postgres store remains the single source of truth.
- Preserve tag governance: no SilverBullet-originated tag text ever becomes a governed tag name without going through `TagService`.
- Keep links between bibliophage documents correct regardless of how often a document's derived path changes.
- Turn `[[wikilink]]`s and `[text](relative/path)`-style markdown links into first-class, provenance-tagged graph edges, both consuming them (create edges from what a user types, in either syntax) and maintaining them (keep them consistent with content as it's edited).

**Non-Goals:**
- Supporting non-bibliophage-backed pages in the same SilverBullet space. The space is assumed fully bibliophage-backed throughout this design.
- Supporting SilverBullet's offline/PWA sync mode for this space (see Risks) — an operational constraint, not something this design defends against in code.
- Letting a user delete a markdown-provenance graph edge directly through bibliophage without touching the underlying SilverBullet content. See Decisions — this isn't a missing feature so much as a direct consequence of content being the source of truth for these particular edges.

## Decisions

### The space backend is an HTTP shim speaking `/.fs`, not a SilverBullet fork or FUSE
`python-server` implements SilverBullet's existing `/.fs` REST contract directly; an unmodified SilverBullet client is pointed at it as if it were a normal SilverBullet server.

**Alternatives considered**: (a) a true FUSE filesystem mounted on disk, with SilverBullet's own `DiskSpacePrimitives` reading through it — rejected, requires implementing full POSIX semantics SilverBullet itself doesn't need, since its own storage trait is already this narrow. (b) forking SilverBullet's Rust server to add a native `PostgresSpacePrimitives` — rejected for now, more native but means maintaining a fork; revisit only if the HTTP shim proves insufficient.

### Page path is derived live from `sb_directory` + `name`, not stored or pinned
No path is ever persisted as its own field — it's recomputed as `sb_directory/name` (or just `name` at the space root) from the document's current state on every `GET`/listing. `sb_directory` is a new, plain `documents` column, decoupled from `document_type` and every other tag: it's freely set by filing a page into a folder in SilverBullet, carries no semantic meaning to bibliophage, and is never governed or reconciled through the tag mechanism below. `(sb_directory, title)` is enforced UNIQUE at the DB level, which is what makes wikilink resolution on write unambiguous (see the placeholder decision below) — a document's full path is, by construction, the only document with that path.

New documents default to `sb_directory = 'bpgInbox'` until a user files them elsewhere via SilverBullet — the same convention SilverBullet's own built-in "Quick Note" template already uses (`suggestedName: "Inbox/${os.date(...)}"`, confirmed in `libraries/Library/Std/Infrastructure/Page Templates.md`). `sb_directory` is not exposed in frontmatter: unlike `document_type`, it has no meaning outside of path, so the path itself is its only representation.

**On collisions**: confirmed against SilverBullet's client source that SilverBullet itself can never produce an `(sb_directory, title)` collision — every page-creation code path (`template.createPageFromTemplate`, create-page-under-cursor for a dangling wikilink, Copy Page) checks `space.pageExists`/`getPageMeta` first and refuses or redirects rather than creating a second page at an existing path; a path is a page's identity in `SpacePrimitives`, so "two pages, one path" isn't representable client-side at all. The only avenue that can actually produce a collision is bibliophage's own non-SilverBullet document creation (PDF ingestion, web-ui) — most plausibly two documents both landing in the shared `bpgInbox` default with the same title. The shim checks for this before insert and appends a UUID-tail suffix, so the UNIQUE constraint is always satisfied by construction rather than ever rejecting a write.

**Alternative considered**: derive path from `document_type` + `name` (this design's original approach) — superseded, see the tag-reconciliation decision below for why `document_type` was pulled out of path derivation entirely. A flat, name-only namespace (this design's second approach, briefly adopted) was also superseded: it left wikilink resolution genuinely ambiguous whenever two documents shared a title, since nothing prevented that and a bare wikilink rarely carries a disambiguating suffix. `sb_directory` restores the uniqueness a real SilverBullet space gets from folders, without coupling it back to any tag. A pinned/stored path was considered and rejected for the same reason as always: it's a second place the path lives that needs invalidating on every rename, which the placeholder-link decision already makes unnecessary.

### Document identity travels in frontmatter, not in the request path
Every generated page carries a reserved, read-only frontmatter field (e.g. `bpg_id`) with the document's UUID. A `PUT` is correlated to a bibliophage document by reading this field out of the submitted content, never by matching the request path.

**Why this is needed**: once the path is no longer pinned (previous decision), it can't double as a stable key either. SilverBullet's rename is literally `write(newPath, content)` then `delete(oldPath)` — two independent `/.fs` calls with no "this is a rename" signal (`SpacePrimitives` has no move/rename method) — so path-based correlation would make an ordinary rename indistinguishable from delete-old-create-new. A `PUT` carrying a known `bpg_id` is an edit of that document, full stop; its serving path is simply re-derived from the current `sb_directory`/`name` on the next read, silently overriding wherever SilverBullet's own UI last moved it.  A `PUT` with a nonexistant / broken `bpg_id` is handled as an error. A `PUT` without a `bpg_id` is a new document. This is the same technique as the link-placeholder decision below, applied to a document's own identity instead of to references between documents.

**On copying/hand-editing `bpg_id`**: nothing at the protocol level stops a user from copy-pasting a page's frontmatter — `bpg_id` included — into an unrelated page, producing two documents that both claim the same identity. The generated frontmatter carries a comment telling the user not to copy or modify the field; beyond that, no server-side detection or reconciliation is planned. This is single-user, self-inflicted misuse, not a case worth designing around.

### Frontmatter `tags` are validated and reconciled on write, not merely rendered on read
Reverses this design's earlier stance that all frontmatter, tags included, is fully server-generated on every read and never accepted from a write. Only `tags` is reopened; every other frontmatter field (`bpg_id`, and the new `bpg_modified` below) stays server-authoritative and is never interpreted as user intent beyond round-tripping.

On every `GET`, `tags:` is rendered using the existing `name/value` hashtag convention (`genre/fantasy`, `document_type/rulebook`), unchanged from today.

On every `PUT`:
1. The shim parses `tags:` from the submitted frontmatter into `(name, value)` pairs.
2. Every tag *name* referenced must already exist in bibliophage's governed tags table (`tags.title`) — an unknown name rejects the entire write with a clear error, no partial apply. An unknown *value* under a known name is accepted and auto-created, mirroring the existing `_apply_document_tags`/`AssignTagValues` rule that tag names are governance-only while values are open (see `define-and-assign-tags`).
3. If validation passes, the shim diffs the parsed set against the document's currently-assigned tag values and reconciles by the delta only — newly-present values are assigned, newly-absent values are removed — not a full replace. This reuses whatever `AssignTagValues`/`DeleteTagValues` (`define-and-assign-tags`, task 2.3) end up being once implemented, rather than bypassing them.

### Submitted frontmatter never becomes part of stored `content`
Whatever frontmatter block a `PUT` carries is parsed for the fields the shim cares about (`bpg_id`, `bpg_modified`, `tags`) and then discarded — the frontmatter text itself is never written into `documents.content`. Storage holds prose only; the frontmatter block is a pure view, synthesized fresh from `documents`/`tags`/`tag_values`/`map_documents_to_tags` on every `GET`, never persisted verbatim anywhere.

**Why this needs to be explicit**: without it, a naive implementation stores whatever the client submitted (frontmatter block included) directly into `content`, and the next `GET` would then prepend a second, freshly-synthesized frontmatter block on top of the first — visibly duplicating on every edit cycle, and leaking YAML noise into the content-snippet/embedding/search pipeline the same way unexpanded link placeholders would (see Risks). The `PUT` handler must strip the frontmatter block from the submitted body before the `character_count`/`content` write, symmetric to how it must already parse that block out to extract `bpg_id`/`tags`/`bpg_modified` in the first place.

### A round-tripped `bpg_modified` field guards tag reconciliation (and content writes) against lost updates
Sibling mechanism to `bpg_id`, needed because reconciling `tags:` by diffing (previous decision) is only safe if the diff is against data the client actually saw. Without a guard, a `PUT` reflects whatever `tags:` looked like at the client's *last* `GET` — and SilverBullet always resends the *entire* document on every save, tag edits or not — so a tag change made concurrently through bibliophage's own web UI, between this client's last `GET` and its next `PUT`, would be silently reverted by an unrelated content-only save. This is the same failure mode already found and fixed once in `define-and-assign-tags` (the floating note editor wiping tags on every content save); reconciling from frontmatter reopens it in a new place unless guarded.

Mechanism: a second reserved frontmatter field, `bpg_modified`, holds the document's `updated_at` timestamp as of the last `GET`, generated and round-tripped exactly like `bpg_id` (ordinary frontmatter text, no protocol/header changes — the stock SilverBullet save path (`content_manager.ts` → `client/space.ts:writePage` → `spacePrimitives.writeFile(path, data)`) never passes the optional `meta`/`X-Last-Modified` header on a normal save, so there is no other channel to carry this). On `PUT`, the shim compares the submitted `bpg_modified` against the row's actual current `updated_at`, then performs the tag diff/reconcile and the content update within the *same* transaction that holds the `documents` row lock (`FOR UPDATE`) — the version check, the tag reconciliation, and the content write are one atomic unit, not three separate round trips that could interleave with a concurrent `AssignTagValues`/`DeleteTagValues` call. A mismatch rejects the write outright — no content change, no tag reconciliation.

**On copying/hand-editing `bpg_modified`**: same non-mitigation stance as `bpg_id` above — nothing stops a user from hand-editing or stale-copying this field, and none is planned; a corrupted `bpg_modified` simply causes spurious conflict rejections (a safe-but-annoying failure direction) rather than silent data loss, which is why this is treated the same way, not escalated.

**Rejected write status**: the shim MUST reject both an unknown-tag-name write and a `bpg_modified` mismatch with a 4xx status (422/409 respectively, exact codes TBD in implementation). This is a hard requirement, not a detail left to implementation discretion: `HttpSpacePrimitives.authenticatedFetch` treats any 5xx as `offlineError` and routes SilverBullet into offline-handling instead of surfacing a rejection — a validation or conflict reject returned as 5xx would be actively misleading, not just unhelpfully generic (see Risks).

### A client-side lint check flags unknown tag names before save, independent of the write-time guard above
Uses SilverBullet's existing lint/diagnostics mechanism (`LintEvent`/`LintDiagnostic`, the same one already used for frontmatter YAML validity) to flag a `tags:` entry or hashtag whose *name* isn't in bibliophage's governed set, inline, as the user types — sourced from a tag-name list cached client-side. Purely informational: it does not block saving, and does not replace the write-time validation decided above, which remains the actual enforcement point. The two are complementary, not redundant — lint catches typos early and cheaply; the write-time check is the only one that can also catch a version conflict, which by nature can't be known until write time (see Risks).

**Cache freshness**: the client-side tag-name cache refreshes on a poll interval (exact interval TBD in implementation, not load-bearing enough to fix here) rather than via a push from `TagManager` mutations or a one-time refresh on space open — accepts a bounded staleness window (a just-renamed tag can show a stale squiggle for up to one interval) in exchange for not needing any invalidation signal wired from `TagManager` into the SilverBullet client at all.

### Cross-document links are stored as UUID-based placeholders, not literal path text
`content` never contains a literal link target. Instead it holds a placeholder token, e.g. `{{ bpg.document.<uuid>.sb.path }}`. `GET` expands each placeholder to that document's *current* derived path as real `[[wikilink]]` syntax; `PUT` does the reverse — resolves literal link text (either syntax, see the link-syntax decision below) back to a document UUID and stores the placeholder.

**Why this is the crux of the design**: it's what makes the previous two decisions (unpinned path, path-independent identity) safe. Nothing that can go stale is ever persisted, so no server-side "rewrite every referring document when a target moves" mechanism is needed at all for links between bibliophage-tracked documents — resolution just happens live, every time, at read time.

**Alternative considered**: keep literal `[[path]]` text in `content`, and have bibliophage rewrite it server-side, in every referring document, whenever a target's path changes (scoped via known graph edges, to avoid a full-space text scan). This was the design's working assumption through most of this exploration and is superseded by the placeholder scheme. It's rejected because it creates a circular dependency with the next decision: the set of "documents that reference this one" used to scope the rewrite is the same set the markdown-derived-edge extraction process (below) produces — so the rewrite mechanism depends on an edge index whose own freshness depends on extraction having already run, and the rewrite's own text edit is itself a content modification that would re-trigger extraction. The placeholder scheme collapses all of that into a single, one-directional derivation (content → resolved links, always computed fresh) instead of two mechanisms that have to stay in sync with each other.

### Both `[[wikilink]]` and `[text](relative/path)` syntax are accepted as link input on write; output always normalizes to `[[target|text]]`
SilverBullet already treats markdown-style links as first-class, indexable, rename-aware references, not inert markdown — confirmed in `plugs/index/refactor.ts`'s own rename logic, which rewrites `[text](path)` targets via `absoluteToRelativePath` and pulls candidates from the same `"relation"` index used for wikilinks, filtered by `_.toTag ~= "url"`. Extending the placeholder mechanism to cover both is additive to the write-time link scan, not a redesign.

On `PUT`, the shim scans for both `wikiLinkRegex` and `mdLinkRegex` matches. Each `mdLinkRegex` match is classified the same way SilverBullet's own relation index already does: an external URL (`http(s)://`, `mailto:`, etc.) is left as literal text, untouched; an in-space relative path is resolved to an absolute target and converted to a placeholder like any wikilink. The one genuinely new piece: a markdown-link's path is relative *to the referring document's own current `sb_directory`*, not absolute like a wikilink target — resolving it means combining the referring document's current `sb_directory` with the written relative path, ordinary relative-path math mirroring SilverBullet's own `relativeToAbsolutePath`/`absoluteToRelativePath` convention so the two stay consistent.

On `GET`, every placeholder is always expanded as `[[target|text]]` wikilink syntax, regardless of which syntax form produced it originally — markdown-link input isn't preserved as markdown-link output. This is deliberate, not a shortcut: wikilinks and markdown-links get materially different treatment in SilverBullet's own client (`client/codemirror/wiki_link_processor.ts` vs. `client/codemirror/link.ts`) — only wikilinks get a missing-vs-existing distinction (`linkStatus: "file-missing"/"default"/"invalid"`, distinct styling, "Create X" vs "Navigate to X" tooltips), page-decoration theming, and a short-path display toggle. More importantly, the click-to-create-stub interaction the aspiring-page mechanism depends on is wikilink-only at the command level, not just styling — `createPageUnderCursorCommand` (`plugs/editor/navigate.ts`) only ever looks for a `WikiLink` node under the cursor. Normalizing to markdown-links on output would silently break that affordance for every dangling reference; normalizing to wikilinks preserves it and every other native-link feature, regardless of which syntax a user typed.

**Alternative considered**: preserve original syntax fidelity (remember which form produced a placeholder, regenerate the same form on read). Rejected — it would require the placeholder representation to carry a syntax-form flag, for no benefit beyond cosmetic preference, given every functional advantage sits on the wikilink side.

### `[[wikilink]]`s and markdown-style links are both a write-time source of graph edges, not just a read-time rendering concern
On every `PUT`, links of either syntax resolved during the literal-text → placeholder conversion produce or update graph edges tagged with provenance `markdown`. `Edge` gains a `source` field distinguishing `markdown`, `user_input`, `llm_determined`, `vector_similarity`, `keyword`, etc.

### A markdown-provenance edge's lifecycle is driven entirely by its placeholder's presence in content
There is no independent "delete this edge" operation in bibliophage for markdown-provenance edges.

**Rationale**: content is the authoritative source for these edges. SilverBullet always resends a document's full body on save (there's no partial-update path), so re-running wikilink resolution against the latest body on every `PUT` naturally reflects both additions and removals — a placeholder that no longer corresponds to any current wikilink simply isn't regenerated. Deleting such an edge only through bibliophage's own UI, without also stripping the corresponding placeholder from stored content, would silently reappear the next time that document is saved from SilverBullet — this isn't a feature deferred for simplicity so much as a direct structural consequence of the placeholder decision. It applies only to markdown-provenance edges: `user_input`/`llm_determined`/`vector_similarity`/`keyword`-provenance edges have no backing placeholder anywhere in any document and are freely creatable/deletable through bibliophage directly, unaffected by this constraint.

### Reconciliation is a placeholder/edge diff, not a text-and-path scan
Because a placeholder already embeds the target UUID, verifying consistency needs no path resolution: it's "does a placeholder exist in some document's content for every markdown-provenance edge naming that document, and vice versa." This can run as a full rebuild at any time (documents → edges is a pure, one-directional derivation, so the edge table never holds information `content` doesn't already contain) or incrementally, queued whenever a document's content changes — mirroring the existing async `EmbedDocument`-after-`StoreDocument` pattern so the write handler itself stays fast.

One exception: the literal-text ⇄ placeholder substitution itself must happen synchronously within the `PUT`, not deferred to an async job — otherwise literal path text would sit in `content` even briefly, reintroducing the exact staleness the placeholder decision exists to eliminate. Only the edge-table bookkeeping (dedup, provenance updates, garbage collection) needs to be async.

### Placeholder syntax is `{{ bpg.document.<uuid>.sb.path }}`, deliberately not `${...}`
Double-curly is inert to SilverBullet. Space Lua's own live-interpolation syntax is `${...}` (`${query[[...]]}`, `${spacelua.renderApiDocumentation(...)}`); if a placeholder were ever exposed to SilverBullet unexpanded (a bug in the shim), `{{...}}` would render as harmless literal text, whereas `${...}` would be actively evaluated as a Lua expression. A deliberate defense-in-depth margin, not just a style choice.

### `document_type` becomes mandatory, may hold multiple values, and may be inferred from avenue of ingress
Reverses `document-classification`'s "a document may have no `document_type` tag" allowance: that allowance existed to keep the `publication_type`/`Pdf.type`-to-tag migration honest (untyped documents were an expected, transitional side effect of a migration with no backfill), and that migration is complete once this change ships — going forward, every document gets a `document_type`. If none is set explicitly, bibliophage assigns one: an educated guess based on the avenue of ingress where a reasonable one exists for that avenue, falling back to `"generic"` otherwise. This also reverses "PDF ingestion does not infer a document type," which existed for the same migration-safety reason and is no longer needed.

While editing this requirement, corrected an inconsistency the rest of this design already assumed but the current spec text didn't allow: the existing requirement says `document_type` holds "a single value." Real documents often genuinely belong to more than one type at once (a book that's both `rulebook` and `reference`, say) — the delta spec now allows one or more values, independent of any SilverBullet-specific mechanism.

**Scope note**: this decision states the *principle* (assign a default; infer from avenue where reasonable) and settles it fully for the two SilverBullet-specific avenues below. For every other avenue — PDF ingestion included — the default is simply `"generic"`, with no per-avenue inference logic. This is a deliberate simplicity choice, not a placeholder: PDF ingestion in particular has little left to infer *from* anyway, since `Pdf.type` (the field such an inference would have read) was removed by `define-and-assign-tags`. A smarter per-avenue default can be added later for a specific avenue if one turns out to be worth the complexity; none is designed here.

### A `PUT` at a new path is a rename (of `name` and/or `sb_directory`), resolved immediately — and aspiring pages are just documents with a `stub` tag
A `write` whose path doesn't match a document's current derived path is unambiguously a move/rename: `name` and/or `sb_directory` are updated to match the new path's filename/leading directory, in the same request, via the identity mechanism above (`bpg_id` correlates the write to the document regardless of path). There's no multi-valued ambiguity to resolve here — both fields are single-valued, unlike the folder-based `document_type` reclassification this replaced, which needed a pending-state dance specifically because *which* of several tag values a folder-move affected wasn't always inferable from a single `write`. A `write` whose `bpg_id` isn't recognized at all is simply a new document, its path read as `sb_directory`/`name` immediately (defaulting to `sb_directory = 'bpgInbox'` if the chosen path has no directory component).

Aspiring pages (documents auto-created for a dangling `[[wikilink]]`) are simply a document with a `document_type: stub` tag value, defaulting to `sb_directory = 'bpgInbox'` like any other document with no explicit placement. "Promoting" one out of stub-ness is an ordinary tag edit (add the real `document_type` value, remove `stub`) through the frontmatter reconciliation mechanism already decided, not a path/move gesture — the user is of course still free to also file it into a different `sb_directory`, which is an ordinary rename per the paragraph above, independent of the tag edit.

## Risks / Trade-offs

- **[Risk] Bibliophage's own search/embeddings operate on `content`, which now contains placeholder tokens instead of readable link text** — an unexpanded chunk like `{{bpg.document.a1b2...}}` is useless for semantic embedding and won't match a literal search for "Lord Soth" → Mitigation: reuse the same placeholder-expansion function used for SilverBullet's `GET` before feeding content to chunking, embedding, or `SearchDocuments`'s content index, so bibliophage's own consumers always see resolved link text, never raw placeholders.
- **[Risk] Auto-creating a stub document for every dangling `[[wikilink]]` can pollute the document set** — a typo'd or exploratory link becomes a permanent `document_type: stub` document, not just a broken reference → Mitigation: none planned; accepted cost of closing the aspiring-page loop automatically rather than leaving links silently unpromotable. This is single-user software in an exploratory phase (see `openspec/config.yaml`'s project-stage note) — a self-inflicted mess of unused stubs is an acceptable, reversible cost (the store gets purged periodically anyway), not a reason to build cleanup tooling now. A future "merge/delete stub" cleanup path is out of scope for this change (no merge operation exists yet at all, per `define-and-assign-tags`'s design) and should only be built once actually needed.
- **[Risk] SilverBullet's offline/PWA sync mode must never be engaged for this space** — its service-worker `SyncEngine` maintains an independent IndexedDB mirror via a timestamp-based sync algorithm; every regenerated frontmatter or placeholder-expansion would look like a remote-side change worth reconciling, likely producing spurious `.conflicted-copy` files → Mitigation: operational constraint (don't install this space as an offline-capable PWA), not something enforced in code by this change.
- **[Risk] SilverBullet's stock save-failure UX doesn't distinguish rejection reasons** — `content_manager.ts`'s save handler shows a generic "Could not save page, retrying again in 10 seconds" for *any* failure — an unknown tag name, a `bpg_modified` conflict, or a real network blip — and retries indefinitely with the same unchanged body, so a genuine rejection of either kind loops forever with no explanation ever surfaced to the user → Mitigation: none planned against the stock client; out of scope for this change. The lint check reduces how often the unknown-tag case reaches this state at all, but a version conflict can only be detected at write time and has no equivalent early-warning path today.

## Migration Plan

1. No backfill. Per this project's current stage (rapid prototyping, data considered replaceable, database purged regularly — see `openspec/config.yaml`), this change performs no data migration. Placeholder-based link storage and mandatory `document_type` apply prospectively, to documents created or edited after this change ships; pre-existing literal `[[wikilink]]` text or untyped documents are left as-is rather than swept and converted. Revisit if/when this project moves past rapid prototyping and existing data needs to survive changes.
2. Rollback: the shim is purely additive (a new HTTP surface); disabling it returns bibliophage to web-ui-only editing with no data loss, since Postgres remains the sole source of truth throughout.

## Open Questions

- **`AssignTagValues`/`DeleteTagValues` must bump `documents.updated_at`**: required for the `bpg_modified` conflict guard to catch concurrent tag-only edits (see Decisions). This is a requirement on `define-and-assign-tags`'s still-unimplemented task 2.3, not something `add-silverbullet-interop` can enforce itself — flagged here as a cross-change dependency, not resolved.
- **Anchor-fragment targets** (`[[page#Section]]` / `[text](path#Section)`): how a placeholder should represent a link that targets a specific anchor within a document, not just the document itself, hasn't been checked against either SilverBullet's own anchor resolution (`resolveAnchor`/`isValidAnchorName`) or this design. Applies equally to both link syntaxes now that both are in scope. Not blocking — a link without a fragment still resolves fine — but unresolved.
